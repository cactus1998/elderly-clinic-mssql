# API 規格

規格要短：一頁內寫完，重點是讓實作與驗證有明確依據。

## 存放位置

- 規格寫在 `docs/specs/<slug>.md`，slug 用 kebab-case（例如 `cancel-appointment`）。
- 在 `docs/specs/README.md` 的清單加一列（不存在就建立），狀態寫 Draft，實作完成後改成 Done。

## 原則

- **明確**：不寫「合理範圍」「適當處理」，要寫具體數值與狀態碼（例如 `days` 1 到 365，超出回 400）。
- **涵蓋邊界**：除了正常流程，一定要列出資料不存在、狀態不允許、重複操作、併發操作、參數格式錯誤。
- **可驗收**：每個需求至少對應一條驗收標準，驗收標準要能直接寫成 `api.http` 請求。
- **先澄清**：需求只有一句話時，先列出 3 到 5 個關鍵決策與建議選項（例如「取消要真的刪除，還是改狀態為 CANCELLED？」），跟使用者確認後再寫。
- **以現況為準**：先讀 `database/schema.sql` 確認欄位、約束、狀態值，不虛構不存在的欄位。

## 步驟

1. 確認需求，必要時提出關鍵決策問題。
2. 依下方模板寫入 `docs/specs/<slug>.md`，並更新清單。
3. 有狀態轉換（例如掛號狀態）時，附 Mermaid 狀態圖。
4. 回報規格摘要，建議接著執行 `add-api-endpoint`。

## 模板

```markdown
# API 規格：<功能名稱>（<slug>）

## 目標
<這支 API 解決什麼問題、給誰用（2 到 3 句）>

## 範圍
- **Must**：<沒有就不能交付的功能>
- **Should**：<時間允許就做>
- **Won't**：<明確不做，避免範圍膨脹>

## 使用情境
- 身為 <櫃台人員／護理師／醫師>，我想要 <操作>，以便 <目的>。

## 介面
- 方法與路徑：`<METHOD> /api/...`
- 參數：<名稱、型別、必填、範圍>
- 成功回應：<狀態碼與 DTO 欄位>
- 錯誤回應：<每個狀態碼對應的情境，一律 ProblemDetails>

## 資料庫
- 讀寫的資料表：<...>
- 是否需要交易：<是／否，理由>
- 是否需要新欄位、索引或預存程序：<有就改用 db-change skill>

## 狀態與流程
\`\`\`mermaid
stateDiagram-v2
    [*] --> BOOKED
    BOOKED --> CHECKED_IN : 報到
    BOOKED --> CANCELLED : 取消

\`\`\`

## 邊界情況
| 編號 | 情境 | 預期行為 |
|------|------|----------|
| EC-01 | 掛號不存在 | 404 |
| EC-02 | 兩個請求同時操作同一筆 | 只有一個成功，另一個 409 |

## 驗收標準
- [ ] AC-01：Given <前置條件>，When <請求>，Then <狀態碼與回應>
- [ ] AC-02：邊界情況 EC-01 通過
```

## 與其他 skill 的關係

- `add-api-endpoint`：實作以規格的 Must 範圍為準，不額外擴充；每條 AC 與 EC 在 `api.http` 至少有一個請求。
- `db-change`：規格需要改資料庫時使用。
- `his-security-check`：實作完成後檢查。
