# PRD 同步與回滾

程式改了，PRD 就要在同一輪、同一個 commit 跟著改。PRD 是「現在的系統應該長什麼樣子」的唯一依據，不是開工前寫完就放著的文件。

## 業界做法（本 skill 的依據）

| 做法 | 來源 | 在本專案的落實 |
|------|------|----------------|
| Docs as Code | Write the Docs、GitLab / Google 工程文件慣例 | PRD 放在 repo，和程式同一個 commit；`git revert` 會連 PRD 一起回滾 |
| Living document | 敏捷產品管理（Atlassian、Confluence PRD 模板） | 需求變了就改 PRD 本文，不另開「補充說明」 |
| Definition of Done 含文件 | Scrum DoD | 回覆完成前，PRD 與實作一致才算完成 |
| 文件版本與狀態 | 語意化版本（SemVer）概念、文件控制（ISO 9001 / IEC 62304 的文件管理） | PRD 開頭的版本、狀態、最後更新；改版依下方規則升版 |
| Changelog | Keep a Changelog | 每份 PRD 底部「變更紀錄」表，新到舊 |
| 變更分級與核准 | 變更管理（Change Request / CCB） | 依變更類型決定要不要先問使用者 |
| 需求追溯 | 需求追溯矩陣（RTM），醫療軟體常見要求 | 驗收標準要能對到程式位置與驗證方式；需求改了，對應的驗收標準重新驗證 |
| 決策紀錄 | ADR（Architecture Decision Record） | 決策改變時不刪舊決策，標註被取代並寫理由 |

## 文件結構要求

每份功能 PRD（`docs/PRD-<slug>.md`）標題下方要有：

```markdown
> 版本：1.2.0 ｜ 狀態：完成 ｜ 最後更新：2026-11-11
```

- **狀態**：`Draft`（規劃中）、`進行中`、`完成`、`已取代`（被新 PRD 取代時寫「已取代，見 PRD-xxx.md」）。
- 底部一定要有「變更紀錄」（放在「開發紀錄」之後）：

```markdown
## 變更紀錄

| 版本 | 日期 | 類型 | 內容 | 原因 | 影響 |
|------|------|------|------|------|------|
| 1.2.0 | 2026-11-11 | 需求調整 | 每頁筆數改為 10/20/30/40/50/100 | 使用者要求 | AC-04、PaginationBar |
```

總規格 `docs/PRD-elderly-clinic.md` 的變更紀錄只記一行摘要（日期、內容，依時間由舊到新附加在最後），細節在功能 PRD；範圍變更時總規格升版。

## 變更分級

| 類型 | 例子 | 版本 | 要先問使用者嗎 |
|------|------|------|----------------|
| 範圍變更 | 新增或刪除功能、改變總規格 Must / Should | 主版號 +1（2.0.0） | 要，同意後才改程式 |
| 需求調整 | 改數值、選項、文案、流程、驗收標準、測試資料 | 次版號 +1（1.1.0） | 使用者明確要求時不用 |
| 實作修正 | 修 bug 讓行為符合原本的 PRD、重構、樣式微調但規範不變 | 修訂號 +1（1.0.1） | 不用 |
| 回滾 | `git revert`、撤回先前的調整 | 依被撤回的變更升版，類型寫「回滾」 | 回滾本身不用；回滾後要不要重做由使用者決定 |
| 文字修正 | 錯字、說明更清楚，規格不變 | 不升版，不記錄 | 不用 |

實作修正如果只是讓程式符合 PRD，PRD 本文不用改，但「開發紀錄」要寫發現的問題與修正。

## 步驟

1. **找出變更**：看這一輪改了哪些檔案（`git status`、`git diff`），列出行為上的差異（API、畫面、資料、文案、數值）。
2. **找出對應文件**：用功能名稱或檔案路徑在 `docs/` 搜尋，找出受影響的功能 PRD、API 規格（`docs/specs/`）、總規格；`README.md`、`api/api.http`、相關 skill（例如 `vue-conventions`）提到同一件事時也要改。
3. **分類**：依上表決定類型與版本。範圍變更先停下來詢問。
4. **改本文**：直接把規格、決策、驗收標準改成新的內容，讓 PRD 讀起來就是現在的系統。
   - 驗收標準內容改了：先改成 `[ ]`，重新驗證通過才打勾。
   - 決策改變：決策表加一列，舊的那列在「決定」欄前面加「~~舊決定~~（已改，見變更紀錄 x.y.z）」。
   - 不要把變更寫成散落各處的「補充」「註：後來改成…」。
5. **記錄**：
   - 功能 PRD：升版、更新「最後更新」、變更紀錄新增一列（新的在最上面）。
   - 總規格：變更紀錄加一行摘要並連到功能 PRD；範圍變更時同步改 Must / Should / Could。
   - `docs/README.md`：狀態有變就更新。
6. **自我檢查**（回覆前）：
   - PRD 裡的數值、路徑、狀態碼、文案和程式一致（用 Grep 對照，不憑記憶）。
   - 沒有留下過時的描述（搜尋舊數值、舊名稱，確認已全部更新）。
   - 被改到的驗收標準都已重新驗證，或明確標示未驗證。
7. **回報**：用一兩句話說明改了哪些 PRD、升到哪個版本。
8. **commit**：使用者要求 commit 時，程式和 PRD 放在同一個 commit，訊息 body 寫「PRD：PRD-xxx 1.2.0」。

## 回滾

- **整個變更撤回**：用 `git revert <commit>`。程式和 PRD 在同一個 commit，revert 後兩者一起回到原狀；再新增一列變更紀錄（類型「回滾」，內容寫撤回了哪個版本、原因），版本號繼續往上加，不倒退。
- **只撤回部分**：手動改回程式，依步驟 4 把 PRD 本文改回舊內容，變更紀錄寫「回滾：撤回 1.2.0 的 xxx」。
- **已 push 的歷史**不要改寫（不用 `reset --hard`、不 force push），一律用新的 commit 回滾。
- **資料庫**：回滾牽涉 `schema.sql` 或 `seed.sql` 時，要提醒使用者重建資料庫會清掉資料，確認後才執行。

## 範例

使用者：「每頁改成 10 20 30 40 50 100」

1. 程式：`web/src/composables/usePagedQuery.ts` 的 `PAGE_SIZE_OPTIONS`。
2. 文件：`PRD-master-data.md`（PaginationBar 規格、AC-15）、`README.md`。
3. 類型：需求調整，1.0.0 升為 1.1.0。
4. 本文改成「每頁 10 / 20 / 30 / 40 / 50 / 100 筆（預設 20）」；AC-15 改寫並重新驗證。
5. 變更紀錄加一列；總規格變更紀錄加一行。
6. Grep 舊值「20 / 50 / 100」，確認沒有遺漏。
